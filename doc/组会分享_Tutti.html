📄 论文摘要

Tutti 是一个 以 GPU 为中心的 SSD 后端 KV Cache 存储方案， 旨在解决长上下文 LLM 推理中 KV Cache 卸载到 SSD 时的 严重 I/O 瓶颈。

现有方案（包括 GPU Direct Storage）虽然移除了 CPU 数据路径，但每个 I/O 仍需 CPU 发起， 导致 CPU 仍在控制关键路径上（O(L·N) 开销）。Tutti 通过三项核心设计将 CPU 完全移除 出关键路径：

  • ① GPU 原生对象存储 —— GPU File Pool + P2P Mapping Table，SGL 代替 PRP（HBM 开销 3.75GB → 15MB）
  • ② GPU io_uring —— 零拷贝 ring buffer 实现 GPU 侧异步 I/O 提交/完成，CPU 仅每层加载一次 kernel（O(L)）
  • ③ Slack-Aware I/O 调度 —— 离线 profile + 读写解耦 + SM 隔离，避免资源争抢

🏆 核心结论

  • TTFT 降低 78.3%（vs GDS-enabled LMCache）
  • 请求率提升 2×（1s SLO 约束下）
  • 服务成本降低 27%
  • Crossover Point 达 98.3%（几乎全范围 compute-bound）
  • 达到 DRAM 级性能 + SSD 级无限容量

💡 关键 insight

  • 问题本质：不是 SSD 带宽不够，而是 CPU 无法高效处理海量小 I/O
  • 解法本质：借鉴 BaM/GeminiFS 的 GPU-centric 思路，让 GPU 自己管 I/O
  • 核心权衡：CPU 管理 Hash 元数据（off critical path），GPU 持有轻量 P2P 映射
  • 工程落地：集成到 vLLM，开源可用，支持单/多 GPU + 跨节点扩展（Mooncake）
  • 局限：依赖 NVIDIA Green Context 硬件特性

LLM推理与KV Cache

Prefill & Decode 两阶段

  • Prefill：处理输入prompt，计算K/V矩阵，compute-bound
  • Decode：自回归逐token生成，每次使用之前计算的KV

KV Cache = 用存储换计算

  • 缓存 Key 和 Value 矩阵，避免 decode 阶段重算
  • Prefix Caching：跨请求复用共享前缀的 KV Cache
  • 可降低每 token 成本 高达 90%

Paged KV 内存管理

  • vLLM / SGLang 使用 分页 (paged) 布局管理 KV Cache
  • Block 大小通常 16–64 tokens，按需分配
  • 灵活但导致 非连续 的碎片化内存布局
核心矛盾：
长上下文 → KV Cache 巨大 → HBM 装不下 → 需要卸载到 DRAM / SSD

现有方案回顾：层级 KV Cache 与 GDS

目前 SOTA：LMCache

  • LMCache 是目前最先进的层级 KV Cache 系统（v0.4.2）
  • 支持 HBM → DRAM → SSD 三级卸载
  • 采用 layer-wise compute-I/O 流水线重叠传输延迟
  • 可选集成 GPU Direct Storage (GDS) 加速 SSD 访问

DRAM 层级：效果不错

  • 低延迟、细粒度 cudaMemcpyAsync 可合并为少量 GPU kernel
  • Layer-wise pipelining 有效隐藏 DRAM→HBM 传输延迟
  • 接近纯 HBM 性能——但 DRAM 容量有限（~2TB）

🤔 那为什么不用 LMCache + GDS 解决 SSD 问题？

GDS 看起来似乎是完美的解决方案——它允许 GPU 通过 DMA 直接访问 SSD，绕过 CPU 内存拷贝。 但下一页会看到，GDS 的 控制路径仍然依赖 CPU，并没有解决本质问题。

GPU Direct Storage (GDS) 是什么？

✅ 它做了什么

  • 允许 GPU 通过 peer-to-peer DMA 直接从 SSD 读取数据到 HBM
  • 消除了 CPU 内存中转（bounce buffer）→ 零拷贝数据路径
  • 减少了 CPU-GPU 之间的数据拷贝延迟

❌ 它没做什么

  • 每个 I/O 仍需 CPU 发起和同步（调用 cuFile API）
  • CPU 在控制路径上处理 O(L·N) 次 I/O 提交
  • 面对大量小 I/O 时，CPU 成为瓶颈——而非 SSD
  • I/O 提交的软件开销（syscall、中断）依然存在
  • GPU 不能自主发起 I/O，仍受制于 CPU 调度
一句话： GDS 解决了 数据路径（GPU ↔ SSD 直连）， 但没有解决 控制路径（CPU 仍在每个 I/O 的关键路径上）。
→ 仍然是 CPU-centric 的设计。

GDS 为什么不够？

CPU 仍然在关键路径上

  • GDS 移除了 CPU 数据路径（零拷贝），但 每个 I/O 仍需 CPU 发起
  • 分页布局 → 大量小尺寸随机 I/O → CPU 成为瓶颈
  • CPU 在控制路径上做 O(L·N) 工作

I/O 碎片化严重

  • Qwen3-32B，64-block，128K tokens → 约 256K 个分散的 80KB 对象
  • vs DRAM：cudaMemcpyAsync 可合并 → 少量 GPU kernel
  • vs SSD：大量随机小 I/O → 带宽利用率极低

💡 为什么 layer-wise 流水线（LW）在 SSD 上反而更糟？

  • Layer-wise = 将传输分成更小的批次以 overlap 计算
  • 但在 SSD 上这导致 更小的 I/O 粒度 → 更多 I/O 操作数 → 更大的 CPU 调度开销
  • DRAM 能受益于 LW（低延迟、细粒度访问），而 SSD 反而受害
  • 本质矛盾：SSD 需要大块连续 I/O 才能饱和带宽，但 paged KV 布局天生碎片化

设计总览：GPU-Centric 架构

Figure 1: CPU-Centric (LMCache w/ and w/o GDS) vs GPU-Centric (Tutti)。Tutti 将 CPU 从关键数据路径和 I/O 控制路径中完全移除。
核心理念： 将 CPU 从关键数据路径和控制路径中 完全移除，让 GPU 自己管理 I/O。 CPU 仅负责异步加载 I/O kernel（每层一次，O(L)），不再是瓶颈。

三大关键技术

① GPU 原生对象存储

GPU File Pool + P2P Mapping Table，对齐 KV Cache 语义，SGL 代替 PRP 减少 HBM 开销

② GPU io_uring

零拷贝 ring buffer，GPU 侧异步 I/O 提交/完成，SM 分区隔离

③ Slack-Aware 调度

离线 profile 窗口 + 读写分离调度，避免带宽冲突和 SM 争抢

8 / 18

① GPU-Centric 对象存储

GPU File Pool & P2P Mapping

  • 每个 memory block → 一个 object（K 对象 + V 对象）
  • GPU file = 2 × L 个 object（L 为层数）
  • Tensor-Stripe 布局：按 tensor 粒度 striped，而非细粒度 striping
  • 预分配 NVMe file pool，启动时完成，运行时零分配开销
  • P2P 映射表：KV Cache 虚拟地址 → PCI 物理地址，启动时预计算
  • 关键优化 SGL 代替 PRP：HBM 开销 3.75GB → 15MB

Figure 3: GPU vs CPU Hash 性能深度分析

❌ GPU Hash 为何如此之慢？

  • Insert：GPU 比 CPU 慢 9.0×–24.2×
  • Lookup：GPU 比 CPU 慢 25.6×–51.0×
  • 1M 序列下 GPU lookup 需 860ms——这比一次完整的 SSD I/O 还长

💡 根因：Hash 天生不适合 SIMT

  • 顺序依赖链：每个 block 的 hash 计算依赖前一个 block 的结果，无法并行
  • 指针追踪（Pointer Chasing）：hash 冲突解决需要链表遍历，不规则访存
  • 控制发散：warp 内不同 thread 访问不同 bucket，路径不同 → SIMT 效率极低
  • GPU 的 大规模并行性无法被利用，反而因线程间互相等待导致更差

✅ Tutti 的设计结论

  • 不能在 GPU 上做 KV Cache 的 Hash 索引管理——这不是 GPU 擅长的负载
  • Tutti 的解法：CPU 管理 Hash 元数据（off critical path），GPU 只持有 I/O 提交所需的 P2P 物理地址映射表
  • 从此 CPU 运行时代价从 O(L·N) 降为 O(L)：每层仅加载一次 kernel，不再逐个发起 I/O

Figure 4: GPU-Centric KV Cache Store 架构详解

📊 架构组件解读

图为 GPU-centric KV Cache Object Store 的整体架构，从 GPU HBM 到 NVMe SSD 的分层设计。

① GPU 侧组件（上图）

  • GPU KV Cache Pool：HBM 中预分配的 KV block 集合，包含 K 和 V 的分块
  • P2P Memory Mapping Table：将虚拟地址映射为 PCI 物理地址（SGL 格式），供 GPU 直接提交 I/O
  • Memory Blocks：按层（Layer 0…n）组织的 KV block，每个 block 包含 K 和 V 两部分

② GPU File Pool（中图）

  • 每个 GPU file 包含 2×L 个 object（每层一个 K object + 一个 V object）
  • Object 粒度与 inference engine 的 block 粒度对齐
  • GPU file 对 inference engine 可见，提供 Store/Retrieve 接口

③ NVMe File Pool（下图）

  • 由 GeminiFS 管理，作为物理存储 extent
  • Tensor-Stripe 布局：按 tensor 粒度 striping 到多块 SSD
  • Round-Robin 放置：均匀分布 I/O 负载，饱和聚合 NVMe 带宽
总结： Tutti 将 Hash 管理留在 CPU 上（做 CPU 擅长的事）， 同时将 I/O 提交交给 GPU（做 GPU 擅长的事）， 实现 CPU-GPU 分工协同，CPU 开销从 O(L·N) 降至 O(L)。

SGL 优化：消除 PRP 内存与带宽瓶颈

PRP 的两个问题

① HBM 浪费

60 GB KV Cache → PRP 需要 3.75 GB HBM 用于地址映射

② PCIe 通信开销大

PRP 命令需要大量 descriptor，单线程读写带宽极低

SGL (Scatter Gather List)

  • 每个条目仅 16 bytes（物理地址 8B + 长度 4B + ID 4B）
  • HBM 开销：仅 15 MB（↓ 256×）
  • 减少 PCIe 通信开销，稳定队列进度

② GPU io_uring (gio_uring)

设计思想

  • 模拟 CPU-side io_uring，完全在 GPU 侧运作
  • "CPU-prepared, GPU-executed" 模型
  • CPU 预填充 IOCB，GPU 执行时零 CPU 干预

关键组件

  • Zero-Copy Ring Buffer：SQ/CQ 驻留 GPU HBM，CPU 通过 non-cached mmap 写入，避免运行时内存分配和拷贝
  • IOCB/IOCTX：每个 IOCB 含 2048 个 IOCTX，每个 IOCTX 记录 SGL 地址 + GPU 文件偏移 + 长度
  • SM Partitioning：通过 NVIDIA Green Context 隔离 I/O domain 和 Compute domain，避免 I/O kernel 阻塞计算 kernel

I/O 流程

  1. init_queue(depth) → 创建 SQ/CQ（depth 个 IOCB）
  2. get_iocb(nums,event) → 填充 IOCTX（CUDA event 保证依赖顺序）
  3. issue_io(IOCB_ids,SMs) → 启动 GPU I/O kernel；GPU 生成并提交 NVMe 命令，写 doorbell
  4. wait_cqe() → 在 GPU 上轮询 CQ 完成，无需 CPU 参与
效果： GPU 可一次发起 数千并行 I/O 请求，饱和 SSD 带宽。

📊 图表解读

图为 gio_uring 的架构与 I/O 处理流程。图中分为 CPU 和 GPU 两个角色：

① CPU 侧职责（浅色区域）

  • 1. Create SQ/CQ：初始化一对 lock-free ring buffer（Submission Queue / Completion Queue），位于 GPU HBM 但通过 non-cached mmap 映射到 CPU 地址空间
  • 2.1 Get IOCBs + 2.2 Fill IOCTXs：从 SQ 获取空闲 IOCB 槽位，填充 SGL 地址、GPU 文件偏移、长度等信息。插入 CUDA event 保证 I/O 在计算依赖完成后才执行
  • 3.1 Launch Kernel：将 I/O kernel 和 model compute kernel 一并 enqueue，由 GPU 侧调度执行

② GPU 侧执行（深色区域）

  • IOCB 结构：每个 IOCB 含 idx、num_ioctx、event 字段，一个 SQ entry 对应一个 IOCB（而非单个 I/O 命令）
  • IOCTX：每个 IOCB 含多达 2048 个 IOCTX，每个 IOCTX 代表一个 I/O 上下文（SGL 地址 + 偏移 + 长度），对应 GPU 最小调度单元（SM/Warp）
  • 3.2 Issue I/O：GPU kernel 遍历 IOCB 中的所有 IOCTX，批量生成 NVMe 命令写入 Submission Queue，最终写 doorbell 通知 SSD
  • 4. Poll CQ：GPU 轮询 Completion Queue，I/O 完成后自动进行下一步处理
  • Storage 与 Compute 通过 SM Partitioning 物理隔离，互不干扰

💡 与传统 CPU io_uring 的关键区别

传统 CPU io_uring：1 SQ entry = 1 I/O 命令。gio_uring：1 SQ entry (IOCB) = 2048 个 IOCTX，每个 IOCTX 就是一个 I/O 上下文。这种批量化设计使得 GPU 能够一次提交数千个 I/O 请求，充分利用 NVMe 的并行能力。

③ Slack-Aware I/O 调度

两大干扰问题

读写带宽冲突

并发 R/W 总带宽 下降 60%（NVMe 内部缓存竞争）

SM 资源竞争

长 I/O kernel 阻塞 compute kernel（非抢占式调度）

调度策略

  • 离线 Profiling：按 (input_len, prefix_len) 索引 slack window
  • Read 优先：preload 阶段 Read 在关键路径上
  • Write 延迟：仅在 slack window 内发 write，否则 defer
  • Decoupled R/W：避免 layer-wise 流水线的 R/W 并发

Figure 6: 并发 vs 解耦 R/W 带宽对比

📊 图表解读

Real-time PCIe 带宽跟踪。横轴为时间（ms），纵轴为吞吐量（GB/s），蓝 = PCIe Read，橙 = PCIe Write。

❌ 图(a) 并发 R/W

  • Read 和 Write 同时进行 → 带宽冲突严重
  • 总带宽从 40+ GB/s 降至 ~16 GB/s
  • 下降 60.1% — NVMe 内部缓存无法同时服务 R/W
  • naive layer-wise pipelining 的问题：写前一层 KV + 读后一层 KV

✅ 图(b) 解耦 R/W

  • Read 和 Write 时间片分离，不并发执行
  • 总带宽恢复到 40+ GB/s，接近设备极限
  • Tutti 策略：先调度所有 Read，再在 slack window 内调度 Write

Figure 7: Slack-Aware I/O Scheduler 工作原理

📊 图表解读

Slack-Aware 调度器的整体执行时序图。横轴为时间，从上到下为 SM 利用率、Slack Window、I/O Stream、SQ 队列状态。

① SM 利用率 & Slack Window

  • Prefill 阶段 SM 并非始终满载：Attention 等算子占用低 → 有空闲 SM
  • Slack Window = 有 空闲 SM 且 无 R/W 冲突 的执行窗口
  • Scheduler 通过 离线 Profiling 预知每层的 slack 模式，查表决策

② 事件驱动的 I/O 发射

  • 每层 prefill 开始时查 slack 表判断是否发射 I/O
  • Read kernel（R）发射后在 slack window 内执行
  • Write kernel（W）通过 CUDA event 等待 Read 完成后才启动
  • SQ 中的 I/O 请求排队等待，不抢 compute 的 SM

③ Decode 阶段 Write 刷出

  • Prefill 未完成的 Write 在 Decode 阶段 best-effort 刷出
  • Decode SM 利用率通常比 Prefill 低，有更多 slack
结果：Crossover Point = 98.3%，几乎全范围 compute-bound。

  • LooGLE（超长上下文）：所有 baseline 性能差距更大，Tutti 优势更显著

消融实验与扩展分析

论文通过多组消融实验验证各设计组件的贡献：TTFT vs. 前缀复用、PRP vs. SGL、分布式扩展、延迟分解与成本分析

Figure 11: 不同前缀复用率下的 TTFT 对比

📊 实验设置

固定输入总长度 = 128K tokens，逐步增加缓存前缀长度（16K → 128K），观察 TTFT 变化。前缀越长 → 需要从存储读取的 KV 数据越多 → I/O 负载越大。

✅ 核心发现

  • 112K prefix 下：Tutti TTFT = 3.43s，比 LMCache-SSD（7.84s）快 2.28×
  • vs GDS：Tutti 在所有前缀长度下保持优势，16K 领先 5.8%，128K 领先 61.4%
  • vs DRAM：中低复用（16K-96K）Tutti 甚至 持平或超越 DRAM（↑13.4%），说明 I/O-compute 重叠效果可以抵消 DRAM 的延迟优势
  • 仅极端高复用（>96K）时 DRAM 因纯 retrieval-bound 而反超（Tutti 落后 ≤20.6%）

💡 解读

Tutti 的 I/O-compute 重叠效果极佳，使得 SSD 在大多数场景下接近甚至超越 DRAM 的感知性能。曲线平缓上升而非陡峭，证明带宽利用率高、I/O 调度有效。

Figure 12: 分布式扩展性（2-GPU, 4-Disk）

📊 实验设置

GLM-4-9B-Chat-1M 模型，2 张 H100（NVLink 互联），4 块 SSD。横轴为前缀长度（128K → 640K），纵轴为 TTFT（对数坐标）。

❌ GDS 在长上下文下 OOM 失效

  • LMCache-GDS 在 512K 和 640K 标记为 N/A（无法完成测试）
  • 根本原因：GDS 的 cufile 需要分配 GPU 显存作为 staging buffer，长上下文下 staging buffer 超出可用 HBM，触发 OOM

✅ Tutti 无 staging buffer 开销

  • Tutti 通过 register 接口直接管理 GPU 内存，无需中间 staging buffer
  • 640K prefix 下 TTFT 仅 1.2s，成功完成所有测试
  • 128K prefix 下 TTFT = 155.7s，比 GDS（207.1s）低 ~25%
  • 启示：高性能 I/O 必须与计算深度集成设计，而非作为第三方插件接入

📊 实验设置

固定 prompt 长度 32K，改变 cache hit rate（20% → 100%），将推理延迟分解为 Compute Time（有颜色）和 Bubble Time（蓝色虚线）。横轴为 cache hit rate，纵轴为时间。

⚠️ LMCache-SSD（图a）

  • Bubble time 极高且无法被 computation 隐藏
  • Crossover Point 极低（~50%），过早进入 I/O-bound 状态

✅ LMCache-DRAM-LW（图b）与 Tutti（图c）

  • 两者曲线非常相似，bubble time 均保持极低
  • Tutti 的 Crossover Point = 98.3%（图c中 ★ 位置），远高于 SSD-LW 的 ~50%
  • 平均 bubble time 仅 25ms（93.75% hit 时仅 6ms）
  • Tutti 在几乎整个范围内保持 compute-bound，达到 DRAM 级效率

Figure 14: 推理成本分析

📊 成本模型

Cost = (GPU Cost + DRAM Cost + SSD Cost) / Throughput。采用云定价：H100 $5/h，DRAM $0.0088/GB/h，SSD $0.000082/GB/h（SSD 比 DRAM 便宜约 100 倍）。

✅ 成本对比（每百万 tokens）

  • LEval 1.5 RPS：Tutti = $0.25，GDS = $0.38（↓30%），SSD = $0.52（↓52%），DRAM = $0.36（↓31%）
  • LooGLE 0.5 RPS：Tutti 比 LMCache-SSD 降低 66.2%，比 LMCache-GDS 降低 ~27%
  • Tutti 在所有负载下始终为 成本最低 的方案

💡 成本优势的来源

  • SSD 便宜：每 GB 成本仅为 DRAM 的 ~1/100
  • GPU 利用率高：Tutti 饱和 GPU 计算资源，最大化 tokens/GPU-hour
  • SSD 带宽利用率高：LMCache-SSD 虽然也用 SSD，但 I/O 瓶颈导致 GPU 空闲，单位成本反而更高
  • Tutti = "SSD 的低成本 + DRAM 级性能" 的最佳组合

总结与思考

Conclusion & Discussion
17 / 18

总结

核心贡献

  1. 首个开源 消除 CPU 干预的 SSD-backed KV Cache 方案
  2. GPU-native 对象抽象：桥接 KV Cache 传输粒度与 GPU 存储 I/O
  3. GPU io_uring：异步 GPU 直接对象 I/O
  4. Slack-Aware 调度：避免 GPU 资源争抢，Crossover Point 达 98.3%
  5. 集成 vLLM，实现 DRAM 级性能 + SSD 级容量

个人思考

  • BaM/GeminiFS 的 GPU-centric 思路在 LLM 推理场景的优秀落地
  • "CPU 准备，GPU 执行" 模式在 LLM pipeline 中非常优雅
  • 离线 Profile + 查表调度方案在实践中可行且高效
  • SGL 替代 PRP 优化看似小改动，但收益巨大（31×/91×）

未来工作 & 待改进

  • 远程路径优化：当前远端经 CPU 中转 + RDMA，计划 GPU 发起 RDMA
  • Mooncake 集成：跨节点 KV Cache 共享（本地 Tutti + 全局 Mooncake）
  • 局限性：
    • SM Partitioning 依赖 NVIDIA Green Context 硬件特性
    • 离线 Profile 在模型/硬件变化时需重新生成
    • 大规模集群可靠性有待验证
